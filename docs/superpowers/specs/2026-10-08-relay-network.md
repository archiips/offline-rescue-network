# Signed single-relay process demonstration

## Outcome and boundaries
One project preserves public iPhone and responder iPad workflows, C++ engine and Swift native adapters. This checkpoint demonstrates separate public, relay and responder Mac processes with nonoverlapping endpoint contacts and persistent recovery. Native relay controls are the next checkpoint; do not change Training/direct Secure exchange behavior. Synthetic presets only, macOS14/iOS18 floors, no dependencies or real personal data. No physical-radio, background, agency trust, general mesh or independent audit claims.

## Discovery and alternatives
Baseline b1dd8bc: C++ relay queue41 sanitizer tests, Swift67 tests, Python14 harness checks; separate-process direct secure endpoint CLI, CryptoKit ORS1, Keychain keys/pins and actual bounded Network transport. Current direct retries reseal, while relay IDs must remain stable after restart. Queue owns64 rows, eight attempts, per-flow FIFO and persisted3:1 urgent fairness. It does not authenticate metadata or removal.

Choose signed opaque wrapper plus exact-ciphertext cache backed by the existing C++ queue format. Reject simultaneous socket proxy (cannot survive nonoverlapping contacts); reject full BPv7/new crypto library (unnecessary dependency/protocol scope). C++ retains custody/cache/pending receipts; Swift is the Apple crypto/socket adapter. A read-only C ABI lookup reuses the validated queue without consuming attempts. Cached rows bounded64; no silent eviction or renewal. Endpoint cache is per key epoch beside its endpoint DB; it contains ciphertext and hashes, never keys/plaintext. One active owner per root/role. Relay receives only two manually pinned public cards and configured loopback destinations, no endpoint Keychain record.

## Wire contract
Custom sample protocol, not BPv7 interoperability. All integers big endian; strict exact length and no trailing bytes. SHA256 yields lowercase hex ID. Signed domain-separated formats:
- ORL1: magic4, kind1 (0 event/1 device receipt), urgency1 (0/1), expiry8 (positive Int64), hops1 (exactly2 for this one-relay topology), sender card digest32, recipient digest32, correlation32 (allzero event, original ORL1 SHA256 for receipt), sealed length2, ORS1 sealed181...3919, Ed25519 signature64. Overhead177, total358...4096. Signature domain `offline-rescue/ORL1/signature`; covers every unsigned field including ciphertext. Inner ORS1 sender/recipient digests must match wrapper; verify inner ORS1 signature too before admission. Sender/recipient must be the two pinned opposite roles. Receipt priority ordinary; event urgency is author-supplied policy, not body inspection. Event plaintext limit3739 permits wrapper under4096.
- ORA1 destination acceptance: magic4, original outer ID32, destination card digest32, optional return ORL1 length2, return bytes0...4096, signature64. Overhead134, max4230. Domain `offline-rescue/ORA1/signature`. Original ID/destination and signature pinned and matched to selected packet. Event acceptance requires exactly one receipt ORL1 with reversed pins, kind1, correlation originalID; receipt acceptance requires no return packet. Relay must admit return receipt durably BEFORE removing original custody. If it crashes between them, original retries and idempotent receipt caching recovers. Never claim atomic cross-file saves.
- ORC1 upload response: magic4 + outerID32, only confirms local relay admission; unsigned and untrusted, never confirms endpoint delivery or clears origin pending. Endpoint never has a direct-send command/fallback in relay mode.

Use existing LocalExchangeTransport with a new explicit relay-mode initializer/service `_rescue-relay._tcp`,4276-byte frame limit. Preserve original initializer behavior and all deadlines/session/peer limits. Mac hosts disable Bonjour browse/advertisement for this test, use explicit loopback ports. No automatic flush, eight attempts enforced by C++ across restarts. Relay flush selects one global head and connects only to configured destination. No recursive relay forwarding: destination accepts ORL1, relay accepts ORL1 uploads, and topology/config roles are explicit.

## Durable endpoint adapter
Add internal SecureEndpointController relay context method that invokes its existing paired/current/history checks; never expose private keys publicly. Relay endpoint adapter uses raw C++ nextPacket and SecureEnvelope only after those checks. Cache ID hashes domain+kind+own/peer cards+raw inner packet+receipt correlation; cache payload is complete original ORL1. C++ lookup validates/copies exact stored item without pruning or attempts; absent caches create once via CryptoKit and durable enqueue before returning. On hits validate wrapper, expected direction/kind/correlation/metadata and unexpired time; don't silently replace/reseal. Expired cached hits fail closed and require an explicit new sample session. Cached expired rows are not silently removed while a pending event still refers to them. To prevent generic queue pruning causing reseal, refuse cache writes once an expired retained row exists, or give the cache a separate explicit append-only policy that cannot prune. No growing historical registry beyond64.

Destination event acceptance decrypts+commits C++ first, builds/caches encrypted device receipt correlated to originalID, then signs ORA1. If cache save fails, no acceptance returned; committed event retries idempotently. Destination receipt acceptance decrypts+confirms C++ matching pending event BEFORE ORA1; enforce receipt correlation matches durable event-cache ID, including after confirmation/retry. Human acknowledgment remains separate event and encrypted receipt. Duplicate receipt acceptance after pending removed must be idempotent via C++ existing history semantics; verify actual behavior and pin regression.

## CLI and process acceptance
`rescue-relay-host endpoint <0|1> <absolute-root> <listen-port> <relay-port>`: Keychain secure identity, CARD/FINGERPRINT, pair/card/state, preset sos/ack/reply/correction actions, upload, quit; no direct-send address. `rescue-relay-host relay <absolute-store-file> <listen-port> <public-card> <public-port> <responder-card> <responder-port>`: public cards only, custody store, state/flush/quit. A deliberate `flush-drop` command in sample CLI suppresses processing the destination response after receipt to prove lost-response retries, clearly diagnostic. Relay printed status only public ID/role/count/attempt, no keys/text. Endpoint output may show synthetic location. Startup failure nonzero; commands error without resetting stores. Port readiness bounded wait.

Reproducible stdlib Python harness launches subprocesses with bounded reader queues/timeouts and always terminates/reaps exact owned processes. Cards bootstrap and pairing happen before nonoverlapping contacts. Stop responder before public upload, then stop public; kill/restart relay and public to prove original packet ID persists. Start responder while public is absent, flush-drop then restart responder and flush: exactly one SOS, receipt durable at relay while original public pending unchanged. Stop responder then start public; deliver delayed reverse receipt and prove deviceReceived distinct from humanAcknowledged. Repeat delayed explicit acknowledgment and reply through nonoverlapping contacts, clear both outboxes/custody. Negative admission/tamper/forged release tests in Swift, queue fairness/recovery existing C++ tests. Harness must assert endpoint absence at each contact, no direct connection/fallback and relay root has no Keychain files or plaintext location. This is isolated sequential process contact, not OS firewall/radio isolation or distributed machines. Do not publish timings without an actual measurement population.

## Research and critique (2026-10-08)
Primary sources: RFC9180 https://www.rfc-editor.org/rfc/rfc9180.html sections9.6/9.7.3/9.9 (domain separation, no general replay protection, metadata exposure); RFC9171 https://www.rfc-editor.org/rfc/rfc9171.html sections4.4.3/5.5 (bounded forwarding/expiry); SQLite https://www.sqlite.org/lang_transaction.html (transaction boundaries); Apple https://developer.apple.com/documentation/cryptokit/curve25519/signing and https://developer.apple.com/documentation/network/nwlistener (signatures/listeners). Inference: custom signed outer metadata plus saved exact retries needed; these are project decisions, not protocol assurances. Local clock default wall seconds, expiry24h; enforce signed bounded positive timestamp, no trusted-clock guarantee. Replay before expiry may readmit previously removed custody; C++ endpoint dedupe prevents duplicate business event, but adversarial replay can consume bounded slots/attempts. No global replay defense/rate-limit guarantee.

Critique revisions: don't store private identity files at relay; don't use unsigned upload response as delivery; admit reverse receipt before original removal; bind response to exact selected ID; don't let cache pruning renew/reseal expired pending messages; don't advertise an isolated process exercise as physical mesh. Preserve native journeys untouched and verify signed app build. Cache reuse avoids new format/schema/migration; costs bounded64 fixture lifetime and explicit new-session recovery. Header markers aren't auth, local SQLite remains unencrypted; pre-open safety guards retained.

## Amendment — cache binding, cache guard and custody metadata (2026-10-08, parent review)
Parent review reproduced two Important defects with RED probes (`SwiftTests/RelayCacheIntegrityTests.swift`): (1) a same-size, validly own-signed ORL1 for an altered raw message substituted into an existing cache row passed the hit check, because derived ID/flow/sealed length do not cryptographically bind cached bytes to the raw message; (2) deleting only the retry cache while secure history/keys remained let a restarted adapter silently reseal the pending event under a new relay ID. Review also found `RelayService.flush` trusted unsigned queue row metadata.

Corrections (supersede "cache payload is complete original ORL1" above):
- ORF1 internal cache record, never on the network: magic4 `ORF1`, ORL1 length2, ORL1 358...4096, Ed25519 signature64 by this endpoint (428...4166, within the C++ 4276 payload limit). Domain `offline-rescue/ORF1/cache-binding`; signed bytes = domain + exact 64-character mapping ID (domain/kind/own+peer cards/raw/correlation) + record header + ORL1. Verified with this endpoint's own pinned public signing key before the ORL1 is extracted; signed only at actual cache writes. Binding the mapping ID (not just wrapping) prevents transplanting an intact legitimately signed record to another mapping; it avoids decrypting the endpoint's own HPKE output. Hits also require row flow = raw SHA256, priority/expiry equal to the signed packet, stored hops 2, attempts 0, expected direction/kind/correlation/sealed length.
- Received-receipt correlation memo rows use the same ORF1 binding under their own mapping. A memo bypasses the pending-head check only after its record verifies and the bound ORL1 equals the redelivered packet byte for byte; otherwise `cacheMismatch`. Correlation hashes the decoded original ORL1, never the record bytes. A saved event's signatures are checked without its time window, so a receipt still answers an event that expired after delivery.
- Public cache guard `{epoch}.relay-cache.guard`, ORG1: magic4 + own card SHA256 32 + peer card SHA256 32 (68 bytes, no private material). Written exclusively before the cache is first created. Guard present + cache missing/zero-length/invalid → fail closed; cache present + guard missing/mismatched → fail closed (`cacheGuard`). Checked on every use including a retained C++ handle, so a deleted cache is not recreated or written detached. No implicit repair: explicit new session rotates the epoch. Unpaired endpoints create neither file. The secure Keychain record schema is unchanged. Scope: deleting both files together, a crash between guard write and first cache creation (fails closed, needs new session), or any other same-user file writer are outside this local sample guarantee; files are not encrypted or tamper-proof against the local user.
- Relay flush requires row ID = packet ID, flow = SHA256(sender+recipient digests), priority, expiry and remaining hops (stored−1) to equal the signed packet before sending (`custodyMismatch`, custody retained, not forwarded). After the await the complete retained row (metadata, attempts, payload) must equal the selected row before return admission/removal. Serialized flush and reverse-receipt-before-delete order unchanged.
