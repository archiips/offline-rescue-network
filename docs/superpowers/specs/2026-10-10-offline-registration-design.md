# Prepared registration and trusted discovery

## Brief and authorized scope

One rescue product retains public iPhone and responder iPad audiences, C++ durable workflow, Swift crypto/transport and both location research paths. User requires download/register before an outage, then open/send without emergency-time pairing or Transfer; iPad testing is explicitly deferred. User authorized continuing implementation without repeated approval prompts. This design uses that authorization rather than stopping for another spec approval.

## Research and alternatives (2026-10-10)

Existing endpoint cards bind role, signing/encryption keys and epoch; pins currently support exactly one opposite-role conversation. Existing Network Bonjour discovery is untrusted and includes peer-to-peer networking. Preserve its bounded framed sockets, C++ durable receipts and HPKE rather than replacing networking. Apple sources: [CryptoKit signing keys](https://developer.apple.com/documentation/cryptokit/curve25519/signing/publickey), [network API selection](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api), [local-network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy). These support APIs, not an endorsement of this experimental protocol.

Alternatives: names/self-signed discovered cards cannot establish responder authority; online-only login cannot establish new trust during an outage; a prepared issuer public key plus signed bounded credentials permits local verification. Choose the latter for a synthetic enrolled drill. No issuer private key ships in the public app, no personal account data is needed, no UW permission or real agency credential is implied. Production account verification/issuance, server operations and multi-request responder routing are separate milestones.

## First coherent milestone

Build signed credentials bound to an existing endpoint card, realm, serial and validity interval; configured issuer trust, revocation serials and trust-validity cutoff; and a challenge-bound automatic bootstrap between two previously unpaired enrolled endpoints. A public registration authorizes only public role, not responder actions. Use a distinct Bonjour service and protocol domains. Certificates/handshake reveal public identities only; application bodies remain in existing encrypted envelopes. Explicitly label synthetic issuer and single-conversation capacity.

Four frames: public Hello (signed credential + fresh nonce); responder Challenge (signed own credential, hello digest and fresh nonce); public Finish (signed digest of both exact transcripts); responder Ready (signed finish digest). No pin changes on Hello/Challenge/Finish at the responder. Responder treats an exact outstanding Finish as provisional authorization and pins only after the first authenticated encrypted application packet within its ten-second lease; public treats Ready as provisional and pins only after an authenticated encrypted device receipt. Idle/abandoned handshakes save neither pin. Abandoned Finish/lost Ready therefore leaves no saved responder pin. Retries may repeat the exact Finish and recover the same Ready, bounded to the current handshake. Restart/stop discards pending handshakes; existing saved pins are never replaced automatically. Proof expiry, role/realm/key mismatch, forged signatures and revoked/expired credentials fail closed; no plaintext fallback. One active opposite-role peer is an explicit prototype boundary, not a campus inbox.

Preparation accepts trust material via an explicit trusted provisioning boundary; discovery cannot supply or replace the issuer anchor/revocation policy. A credential proves authorization under that configured issuer, not sensor truth, radio proximity or responder availability. Offline revocation can only be as current as prepared trust state; expired trust blocks new bootstrap. Device wall clock remains an unverified security assumption. No indefinite offline registration guarantee.

## Acceptance and critique

Real unpaired secure controllers must establish trust without public-card copying, then exchange SOS/committed receipt/human acknowledgment/reply via existing sockets. Test forged issuer, role/card/realm substitution, expiry/revocation, possession proof, replay, transcript substitution, stop, existing different pin and lost Ready retry. Bounded canonical messages and pending state prevent unbounded allocations. Deduplicate pending handshakes per public key; use the pinned fingerprint only as an untrusted routing hint after pairing. Keep current manual Secure/Training/relay/research intact. Verify reusable enrollment/bootstrap foundation and socket scenario, then native preparation/registered mode with visible credential readiness. Native preparation imports a fully issuer-signed profile, including credential, revocation snapshot and trust cutoff; explicitly verify the organizer fingerprint before import. The real account service remains absent. No fake login form or hardcoded signing secret.

Correctness: four frames avoid committing an unauthenticated advertisement or replayed Hello. Simplicity: reuse secure endpoint persistence rather than introduce a second message engine. Privacy: no email, name or precise location in enrollment; stable public credentials remain linkable during the drill. Maintainability: isolated credential/bootstrap components. UX: preparation happens before outage; no emergency pairing. Testing: synthetic issuer only; physical and organization-readiness gates remain open. Abuse/responder multi-user fairness need later design and are not solved by signatures.
