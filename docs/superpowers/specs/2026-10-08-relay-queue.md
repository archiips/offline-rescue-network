# Opaque relay custody foundation

Build the first C++ relay checkpoint: durable opaque queue, Swift bridge and a process-local encrypted delayed-contact scenario/CLI. Native public/responder and Training stay intact. This does not implement a network listener, authenticated routing metadata or physically isolated multi-hop. Full relay task stays open.

Previously implemented in an uncommitted temporary worktree, then lost when the laptop restarted. Prior passing output is historical, not evidence for reconstructed code. Restore from this contract, verify afresh and commit checkpoints in a persistent ignored project-local worktree. Published baseline d1ac5cb is intact.

## Design and acceptance contract

C++20/SQLite queue, no private keys/plaintext, local trusted callers only. Item: immutable lowercase hex64 ID and flow, urgency0/1, positive signed64 logical expiry, input hops1...2, attempts0...8 and opaque payload181...4276. At most64 retained items and273664 payload bytes, no eviction. Duplicate same ID/all immutable fields/ciphertext returns duplicate1; changed fields conflict5. Expired rows prune transactionally on admission/selection. Expired ID can be reused with future expiry; no replay defense is claimed.

Only oldest nonexpired item per flow is eligible. Exhausted head remains retained and blocks its flow. Across heads, choose oldest urgent unless three urgent selections have occurred and ordinary eligible; then oldest ordinary. Burst counter capped3 and reset on ordinary, persisted. Selection increments attempts before returning; at most8. Returned hop budget decremented once while stored budget remains for same-hop retries. One relay only; no recursive routing claim.

Every operation revalidates schema and row types/bounds/order/counters inside SQLite transaction. Lock/save/commit failure returns no selected bytes and rolls back. Distinct exact schema/application ID/version, reject incompatible/malformed stores without replacing. Avoid SQLite numeric affinity hiding altered text: typeless numeric columns plus explicit SQLITE_INTEGER checks. Bounded admission counter signed64, overflow fails safely. SQLite ownership must be RAII even when initialization throws (previously reproduced leaked descriptors3→13 after10 rejected opens and fixed). C ABI allocated selected item has exact free; Swift copies and frees on every path.

API RescueRelay.h: opaque rc_relay; rc_relay_open(absolute path), destroy, enqueue(id,flow,urgency,expiry,hops,payload,length,now), select(now,owned item**), remove(id), count(size_t*), item_free. Codes0success,1duplicate,2invalid,5conflict,6capacity,7storage,8empty/absent,-1null handle. Selected item ID/flow arrays65, urgency, int64 expiry, remaining_hops, attempts, pointer+length. Add explicit module.modulemap exposing existing RescueDemoBridge.h and new RescueRelay.h, no changes to existing C API.

SQLite deletion means caller validated endpoint receipt or explicit administrative deletion, not proof verified by queue. Custody must not clear sender C++ outbox. Logical time is deterministic caller time, not production clock freshness. Rows/bytes bounded, no unlimited-lifetime filesystem-size guarantee.

Swift MainActor RelayQueue storageURL, throwing init/enqueue/select/remove/count, owned handle. RelayPriority ordinary/urgent, immutable RelayItem, typed RelayError code. RelayScenario.run(root:) runtime SecureIdentity+SecureEnvelope objects at endpoints, independent EndpointController SQLite files and relay file, no Keychain persistence. SHA256 exact sealed bytes used as stable sample ID, same ciphertext for retry; current direct adapter reseals retries, future network adapter must persist stable mapping.

Scenario: seal preset SOS, enqueue exact ciphertext twice idempotently; assert relay file includes sealed envelope but no location/inner packet, responder empty and origin pending. Close/reopen queue and endpoint. Destination contact decrypts/commits, drop first receipt; retry exact stored packet, assert one request. Delete local original custody only after responder acceptance, origin still pending. Reverse encrypted receipt gets queued/reopened/delayed, decrypt+confirm at origin clears pending to deviceReceived, not humanAcknowledged. Separate responder acknowledgment relayed plus its reverse receipt, ending both outboxes/queue empty. CLI rescue-relay-scenario fresh temporaryroot, named PASS facts, error nonzero and cleanup. Contacts process-local, never claim radio/socket isolation.

Tests: C++ durable reopen/independent handles, duplicate/conflicting all fields, FIFO/dependency/exhausted head, 3:1 fairness including restart/late ordinary,64max payload/capacity/noeviction/expiry, signed64/input/hop/retry bounds, locks/commit rollback, altered schema/types/counters/payload/rows, incompatible endpoint/training/WAL/junk stores, failed-open descriptor lifetime. ## Research, alternatives and critique

Primary sources checked2026-10-08 before interruption: RFC9171 sections1,4.4.3,5.5 https://www.rfc-editor.org/rfc/rfc9171.html (store-forward/hop/expiry), existing RFC9180 https://www.rfc-editor.org/rfc/rfc9180.html, SQLite https://www.sqlite.org/lang_transaction.html and https://www.sqlite.org/pragma.html#pragma_application_id. Policy choices are project defaults, not RFC interoperability. Socket proxy rejected: requires simultaneous contacts. Full BPv7 stack rejected: unnecessary dependencies/security/routing scope. Correctness: preserve flow prerequisites and persisted attempt/fairness. Simplicity: no new crypto version/socket/native behavior. Privacy: only bytes/routing metadata at queue, trusted-only admission explicit. Maintainability: C++ transactional owner, thin Swift owned-copy bridge. Testing: actual SQLite/CryptoKit + failure paths. UX: both existing native journeys retained, CLI distinguishes queued/delivery/acknowledgment. Future authenticated network routing is explicit next checkpoint.
