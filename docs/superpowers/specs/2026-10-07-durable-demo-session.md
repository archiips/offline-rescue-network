# Durable native training session

One portfolio project with public and responder views, SwiftUI clients and a C++ engine. Preserve every existing SOS/reply/update/handling journey while adding restart recovery. Physical networking and commercialization remain deferred. User authorization covers continued implementation, Claude review and verified public commits; execution is inline.

## Chosen design

Use the system SQLite C library from C++, linked by SwiftPM and CMake, with no downloaded production dependency. One local database stores the two simulated models' event histories in their actual acceptance order, outstanding transfer events in queue order and the simulated connection flag. This is one process/one transaction for a training simulation, not two network devices sharing a database. The C++ domain reducer remains in memory and is reconstructed by validating persisted events through its existing submit/receive rules.

Each action operates on a bounded copy of the current session. Persist the complete resulting state and outbox in one SQLite transaction before publishing the copy to the UI or returning accepted. If the write fails, roll back and retain the previous models, queue and sequence values. Receipts visible after return have been included in the committed simulated session. Opening a store never pumps the queue or fabricates delivery; reconnect remains explicit. Saving reset is transactional and must not resurrect old queued events on reopen.

SQLite uses rollback journaling (DELETE), synchronous EXTRA and fullfsync where supported. Schema version 1, generation checks prevent stale handles overwriting newer state, busy timeout 250 ms, main-file bound 4 MiB and recovery sidecar bound 8 MiB each, pre-open rejection of valid SQLite WAL headers (while allowing hot-journal recovery of zeroed first-transaction headers), exact schema validation on load/save, bounded row/field decoding, models 128 events each and queue 64. A missing or zero-page uninitialized file creates a store (including interrupted first initialization); corrupt, unsupported or semantically invalid existing stores fail closed and are preserved. No silent fallback to an empty session or automatic destructive repair. Swift supplies an app-local Application Support path, shows a startup/save error and permits retrying the saved session or queued transfers. Tests retain optional in-memory sessions.

## Alternatives / limits

Flat-file JSON would require a new C++ parser and manually proving fsync/rename/directory recovery. An append-only custom journal adds torn-record and compaction work. SQLite provides an existing transaction/recovery implementation. Full bounded-state rewrites are deliberately simpler than incremental per-device inbox/outbox tables; later radio integration must split transaction ownership per endpoint. This checkpoint does not freeze the private wire protocol, close ENG-04/M1 or add encrypted storage/authentication. Sample presets remain the only UI data input. SQLite hot-journal recovery may change files before semantic validation; arbitrary sidecars, concurrent file replacement and invalid UTF-8 corruption are not general preservation guarantees. Real hardware power-loss durability is untested and depends on SQLite/OS/filesystem assumptions.

## Acceptance and verification

Close/reopen with an offline SOS and queued return action; preserve correction/reply/handling histories and acceptance-order late flags; reconnect correctly; duplicate receipts do not multiply. Explicit reset stays empty after reopen. Failed saves, locked DB, stale writer, corrupt/unsupported schema and invalid stored events do not silently replace saved data or publish unsaved actions. A child process exiting inside an uncommitted transaction leaves the previous state recoverable. Native simulator terminate/relaunch preserves both role states and disconnected queues. Existing 19 automated checks remain green; added recovery tests, ASan/UBSan, Release and simulator builds pass. Inspect rendered flows and request read-only Claude review before publishing.

## Critique and revision

Correctness: commit precedes observable success; snapshot copying avoids complex undo; persisted acceptance order preserves the command-local late flag. Simplicity: one fixed exercise/request, bounded snapshot store and explicit reconnect. Privacy: preset sample data only; no claims of encryption or secure deletion. Maintainability: isolate SQLite in session_store.hpp/cpp, reuse the reducer and expose narrow open/reset calls. Testing: real transaction failure and process interruption, not only orderly destructor/reopen. UX: failed startup displays an error/retry, never a fabricated empty inbox; reset only reports success after commit. Tradeoff: synchronous small saves can briefly block MainActor; 250 ms lock timeout bounds lock waiting, and field measurements remain future work.
